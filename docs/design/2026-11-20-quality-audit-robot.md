## 2. 判定と保存

- 判定は **PASS（確かめて正常）／FAIL（確かめて異常）／REVIEW（人の確認が要る）／UNVERIFIED（まだ確かめていない）／BLOCKED（この方法では確かめられない）**。未検証を正常として数えない。
- EP-ID 単位で保存する項目: 監査日時・領域・検査項目・判定・根拠（URL・ID・リンク先の題名）・検証方法・問題の種類・修正候補。再検査は同じ形で追記し、前回との差を出す。
- 保存先: `docs/audits/quality/latest.json`（要約＋PASS 以外の項目・疎通の結果）、`latest.md`（管理人向け）、`probes/<日付>.json`（疎通の記録）。本台帳の原本列とは分離。
- 「既に一次情報で確かめた事実」はロボの中の一覧（KNOWN）に根拠つきで持つ（例: SDGs の Spotify 移転、#395）。ここに無いものを推定で異常・正常にしない。

## 3. 監査方式

| 方式 | 中身 | 最小版での実装 |
|---|---|---|
| A. 日次差分 | 新着・更新・清掃・URL補完された回を優先 | 次段（同期の差分レポートを入力にする） |
| B. 全件 | 公開データ全件の内部整合性（URL の登録・形・重複、概要欄・出演者の空欄、再生時間、件数、宇宙と蔵の版） | **実装**（外部アクセスなし・数秒） |
| B'. 外部の疎通 | 各サービス日替わりの抜き取り（既定12件）。開くかだけでなく**リンク先の題名が回の題名と一致するか**まで見る。全件を一度に開かない | **実装**（Spotify 公開埋め込み・Pocket Casts・Omny・Apple・LISTEN。Amazon・朝日新聞公式・Pody は描画が要るため BLOCKED と明記） |
| C. 再検査 | 過去の問題の回を修正後に再検証 | KNOWN と前回結果との差分で追跡（次段で個別の再検査リストに） |
| D. 人の抜き取り | AI だけで決められないものを管理人へ | レポートの「人の確認が要る上位案件」 |

## 4. 安全原則
読み取り専用で始める／本台帳・GAS・公開データを変えない／監査と修正を分ける（自動修正は別設計・承認）／既存ロボと同時に書かない（独立したワークフロー、レポートは `[skip ci]` で再デプロイしない）／失敗しても収蔵・公開を止めない／外部サービスへは間隔をあけて少数ずつ／AI の判定だけで精度100%を主張しない。

## 5. 優先順位
- P0: #395 の Spotify 復旧（PR #399 の対応表 → 承認後に台帳更新 → 全件の再疎通）。Pocket Casts の全件疎通。
- P1: URL 監査（本書の最小版）。全サービスの登録率と抜き取り疎通を毎日。Amazon Music の登録率を報告。
- P2: 概要欄・清掃・出演者（原文と加工後の差分、合格回の抜き取り再検査、概要欄にある名前と出演者欄の照合）。
  - **2026-11-20 実装（公開データで見られる分）**: 利用者に見える文面（表示整形 description-tidy の後）で判定する。
    表示に告知・定型文が残る／表示に HTML の記号（&…;）／整形すると本文が空／別の回と概要が同じ（取り違えの疑い）／
    出演者欄に見出し・説明文が混入／読点・カンマ区切りで1人ずつに分かれていない。すべて REVIEW（人が確認）で、直すのは別作業。
  - 未実装: 原文（RSS）と清掃後の差分、概要欄の名前と出演者欄の照合（原文が公開データに無いため、台帳側の監査として別に作る）。
- P3: 収蔵・分類・公開の横断（公式配信一覧との差分、再配信判定、蔵の検索と台帳の一致）。
