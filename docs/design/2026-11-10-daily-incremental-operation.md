**前提**: 総数は毎日変わる。5,848(2026-10-22掲載判定)や5,945(2026-11-10検証用)は特定日のスナップショットで、固定目標ではない。完成の定義は「明日も明後日も新着を取り込み、正しく更新され続ける」こと。

## 固定件数を前提にした条件の廃止・修正
- `tests/library-publication-browser.cjs`: 「掲載対象5,848件」「5,848個の星」「2026年10月22日掲載判定」の固定文字列を、`scope.json` から導出した件数・判定日に変更。
- `partitionEpisodes`(publication-scope.mjs): スナップショット後の新着・未レビュー等を**黙って捨てず**「pending」として件数化。公開済みの欠落だけが `INCOMPLETE_PUBLICATION_SCOPE` で停止（件数の固定ではなく、公開済みが減らないことを守る）。
- 残している固定値: `library-publication-scope.test.mjs` の 5848/377/366 は「2026-10-22の判定スナップショット」の回帰テストであり、題名に SNAPSHOT を明記。日次の総数条件には使わない。

## 運用フロー（案）
1. 巡回: 公式RSS(許可ホストのみ)を取得 → `ingest`（GUID照合・追記）→ `runRecord`。
2. 保存: 新registry+run記録をCOPY用ジャーナルへ追記（COMMITマーカー方式は既存 P25 state と同型）。本番台帳への書込は別承認。
3. 公開ビュー: 人間が確認済み・対象・承認済みにした分だけが `isPublishable` で公開集合に入る。`publication-scope` は日付つき判定の記録として更新(snapshotDate)し、固定件数を持たない。
4. 監視: `status=STOP` で公開データの更新を止めて通知(通知手段は未設計)。WARN は記録のみ。
5. 再開: 途中失敗は未COMMITとして無視され、次回が同じGUIDから再実行しても重複しない。

## 段階的導入（すべて別承認）
- 現段階(本PR): COPY・モック・READ_ONLY。実RSS取得とジャーナルのCOPY書込は未実施。
- 次: COPY GAS で実RSSを READ_ONLY 取得し registry(COPY)に差分だけ書く → 毎日の run 記録を数日観察。
- その後: 既存トリガー/writerの棚卸し、本番台帳への登録経路、日次トリガー設定、公開データ更新の自動化。

## 未検証・リスク
- 実RSS(複数番組フィード)のページング・過去分の網羅性、GUIDの再発行有無。
- 既存の台帳GASが同じ新着をEP-IDで登録する経路との二重採番(本設計はIDを台帳に合わせる別層が必要)。
- SPOTIFY_LINK_GAP は登録処理の遅れを検知するだけで補完はしない。
