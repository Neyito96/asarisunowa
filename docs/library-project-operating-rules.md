# 朝リスの田｜独立エピソード図書館・継続開発ルール

更新: 2026-10-16

## 作業を再開する前の必須復習
1. この文書、docs/library-backfill-audit-2026-10-16.md、関連GASソース、GitHubの最新コミットを確認する。
2. 直近の「自動補完・実行履歴」を確認し、実行済み・未実行・保留を区別する。
3. 前回の続きを優先する。ユーザーに決定済みの仕様を繰り返し質問しない。
4. GitHubコミットとGAS実行・スプレッドシート更新は別。コードをコミットしただけで本番に反映されたと表現しない。
5. 実行結果の報告は「実施済み」「未実施」「次に必要な操作」を明確に分ける。

## データ・運用の不変条件
- EP-IDを変更しない。既存値を勝手に上書きしない。重複登録しない。
- 人間による削除・除外・保留を尊重し、再登録や自動解除をしない。
- 概要欄の本文に実際の改行を大量挿入してシートの行高を増やさない。後から改行を復元できる表現（文字列 \\n 等）または既存の清掃方式を維持する。
- 「概要原文」と「清掃済み」の意味を混同しない。清掃で情報を落とさない。
- RSSを一次情報源にし、Spotify API依存を減らす。
- RSSの番組名・タイトル・日付が一致してもSpotifyエピソードの同一性が自動的に証明されたとは扱わない。
- 403/429/503、再試行、途中保存、重複排除、取得境界の保護を維持する。
- 読み取り専用監査は台帳を書き換えない。書き込み時は少量試験、変更対象の再確認、追記型の実行履歴を優先する。
- 自動補完の実行結果は既存「自動補完・実行履歴」に残す。監査結果と書き込み実績は区別する。
- 本番公開・既存トリガー変更・大量書き込みは明示的な承認なく実行しない。

## V2高速保管計画の最優先事項（2026-10-16 再確認）
- V2は「高速保管計画」。細切れの手動プレビューを繰り返すことではなく、RSSの並列取得、メモリ上の索引照合、まとめ書き、再開可能な自動処理で既存エピソードを高速に充実させることが目的。
- 既存のV2Writerは80件単位の書き込み・追記履歴・ScriptLock・空欄のみ補完・除外保護を実装済み。これを捨てて新規の遅い仕組みに置き換えない。
- ボトルネック: 台帳6,591件中GUID空欄5,457件。現状のV2WriterはGUID一致のみのため、多数の空欄を対象にできない。番組・タイトル・配信日で4,010件が一意照合された（書込0）。
- 優先する改修: 既存V2のRSS一括取得時に、GUID登録済み照合とGUID空欄の厳密一意照合を統合する。既存EP-IDとSpotify URLを保護し、既存値を変更しない。安全条件を満たす行に限ってGUID・不足メタデータを同じパスで補完する。
- ただし、番組・タイトル・日付一致はSpotify同一性の証明ではない。Spotify URLとの対応確認、重複・再配信・除外の保護を実装してからwriterを有効化する。未検証のまま4,010件を自動書き込みしない。
- 作業のユーザー負担を減らす。既存Google SheetsとGitHubのコネクタで読み取り・コード更新・履歴確認できることは助手が直接実行する。GASの操作が必要なら複数回に分けず一度にまとめる。
- コミットだけでGASが更新されたとは言わない。実際の書き込み件数は「自動補完・実行履歴」で検証する。
