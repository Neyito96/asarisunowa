# Phase15｜数百セル単位の自動補填へ移行する実装指令
2026-10-28。ユーザーの希望：数百セル単位でどんどん実台帳を書き進める。少量COPY報告や監査書面の反復を終了し、測定可能な大量空欄補填を優先。
現在 EP-06633〜06640 収蔵済み、本番P列4セル補填済み。ロボ最新 commit c90eff71a535bdde497618898a60fbe27710680e はGUID一致・空欄のみ・20行処理・次行返却・ロック実装だが、データ取得接続・カーソル永続化・実機実行は未完成。

## 今すぐの実装作業
1. Phase14で既に動作確認したRSS/公式JSON取得と照合処理を探して既存の最新補填関数へ接続。API直接アクセスが失敗した場合でも、既存のApps Script UrlFetchApp公式RSS経路を優先。URLと取得結果の記録を伴うGUID照合を行う。出典が取れない値は絶対推測しない。
2. まず100行／最大300〜500セルを暫定バッチ上限として試験し、処理速度と更新結果から自動調整。GASの実行時間に収まるよう分割し、カーソル・次回再開位置をPropertiesServiceに永続化。エラー行はログに残して次へ進む（整合性が壊れるエラーは停止）。
3. 取得元ごとにGUIDを正規化し、対象セルが更新直前に空欄であることを確認。概要原文/清掃版/音声URL/画像URL/再生時間/公式URL/出演者と取得根拠を優先。既存値は上書きしない。AJW・アルキキ・YouTube等の対象外行をスキップ。
4. COPY専用試験タブで100行相当の模擬・実データ補填と再実行差分0を確認し、次にユーザー承認の範囲で本番の100行実行へ。完了したら連続バッチを複数回実行し、合計更新セル数と処理済み行数を報告。
5. 定時トリガーと新着収蔵は既存本番コードとの競合を避けた単一責任構造にする。複数writerのロック不一致・履歴衝突を防ぐ。まず補填を確実に動かし、自動収蔵の稼働は別の確認点とする。
