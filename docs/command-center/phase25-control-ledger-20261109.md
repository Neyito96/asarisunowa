## 4. 司令塔・Workの責務
**司令塔**：
1. 新指令前にこの文書とIssue #271の**最新の状態変更コメントだけ**を読む。作業済み事項を再依頼しない。
2. Work報告を三つに区分：**証拠確認済／Work報告のみ／未確認**。PR SHA・実機ログの要点・本番変更有無を照合し、曖昧なら「確認できない」と記す。
3. 再発した失敗は「問題ID・再現条件・原因・対策・回帰テスト」で記録。直らないまま同じ指令を繰り返さない。
4. 報告を受けたら現在地・次工程・承認境界を更新し、**一つの次指令**を出す。新たな監査だけを目的とするWork起動を禁止。
5. ユーザーが明示していない本番/削除の承認を推定しない。

**Work**：
1. まずこの文書、PR #270、Issue #271末尾の証拠だけ確認。全履歴の再読・38モック再実行・COPY再構築をしない（変更が関係する場合のみ対象限定再テスト）。
2. 一度の起動で、未完了工程を**できる限り連続して**実装・テスト・コミット・記録。本番の承認ゲートに至るまで停止しない。
3. 変更にはコミットSHA、実際の実行結果、write:false/true、COPY/本番の区分を必ず添える。「ローカルPASS」は「実機PASS」に置換しない。
4. OAuth再認可等の人間操作で停止したら、必要な操作と再開位置を1度だけ報告。同じ確認をループしない。
5. 発見した課題は即時に重大度分類：**BLOCKER（安全/実行に直結）／SEPARATE（例：RSS2253）／LATER（最適化）**。SEPARATE/LATERでPhase25本筋を止めない。
6. 終了時の報告は「到達点｜証拠｜残件｜必要承認｜次の一手」の5項目、簡潔に。

## 6. 障害・再開・復旧ルール
- 429/401/403/5xxやトークン失効を原因別に分類し、失敗した操作だけ再開する。
- Spotify POSTで結果不明の場合、**二度POSTせず membership を読み戻し**、不確実ならHOLD。
- ユーザーがSpotifyで手動削除した項目を再追加しない（tombstone）。
- COPY復旧は追加したEP-06678のみ。ただし削除も現時点未承認であり、復旧実行時は管理者判断。競合変化がある場合は削除しない。
- 本番ロールバックは旧writerへの無条件再接続ではない。ジャーナル・手動除外を維持し、二重書込を防止する。
- テスト用の認可URL・トークン・Client Secretは記録しない。
