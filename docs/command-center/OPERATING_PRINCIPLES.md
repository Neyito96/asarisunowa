# 朝リスの田｜司令塔・各ロボ共通運営方針

制定：2026-11-02　決定者：管理人

> **説明より実行。計画より成果。まず直す。確かめる。記録する。次へ進む。**

## 四原則（管理人承認）

1. **まず既存コードを調べる。** 新しい仕組みやファイルをむやみに増やさず、既存ルール・既知Issue・既存GASを確認する。
2. **最小限の修正を優先する。** 依頼された不具合の解決が先。関連する改善構想は独立Issueへ切り出し、ホットフィックスに混ぜない。
3. **修正→テスト→本番検証まで進める。** PR、モック、単体テストだけでは「完了」と記載しない。既存の安全制約と管理人の承認を守り、本番での動作・再実行時の冪等性・台帳／Spotify／公開サイト整合まで確認する。
4. **報告は短く、実績中心。** **実施済み／未完了／管理人に必要な最小操作**を明記する。未実施の変更、未取得の権限、未確認の成果を完了と表現しない。

## 司令塔の実行規律

- 作業開始時に変更対象・失敗事象・期待結果を各一行で特定する。
- 既存の担当ロボ・処理・トリガーを把握し、一つの問題に不要なロボや設計を巻き込まない。
- コード変更時は再現テスト→最小修正→回帰テスト→既存機能の保護→適切な本番確認の順に進める。
- GitHub上の修正は、実際の本番GAS/Spotify反映を意味しない。**Draft PR = 未配備**。
- 本番台帳、GAS、Spotify、トリガー、公開サイトを変更する際は実際の権限・対象・変更範囲を確認し、必要な管理人承認を得る。
- 既存トリガーの追加・置換や別名の重複関数を避ける。調査ログを大量生産せず、検証可能な成果を残す。
- 個別の不具合修正と、長期のアーキテクチャ改善・データ充実は**別工程**として追跡する。

## 今回の運用例：ノーミライ番外編（Issue #266 / PR #267）

- **直近のゴール**：10月31日配信の番外編が既存Spotifyプレイリストへ反映され、再実行で重複しないこと。
- **原因候補**：番号付き「#」を必須とするタイトル判定が番外編を除外。まずSpotify番組IDを維持したまま既存のマッチ条件だけ修正する。
- **未完了**：Draft PRの本番反映、Spotify個別episode ID照合、プレイリスト差分1件反映と読み戻し確認。
- **別工程**：蔵のSpotify個別URL欠損補完、全件照合、蔵書検索起点の新規プレイリスト構築。Spotify APIの直接取得を廃止しない。

## 共通完了報告フォーマット

- **結果**：依頼された不具合が実際に解消したか（YES / NO / 未検証）
- **実績**：変更ファイル、PR／コミット、検証ログ、本番の具体的な差分
- **残件**：未検証・未配備・保留とその理由
- **次の一手**：実行主体と、必要な一操作だけ

この方針を司令塔・収蔵ロボ・補填ロボ・プレイリストロボ・蔵人の共通基準とする。以前の手順書との衝突時は、運用上の安全制約を保持したまま「小さく確実に完了させる」原則を優先する。
