# Codex 作業ルール — Google Apps Script

このファイルのルールは `scripts/google-apps-script/` 以下のすべてのファイルに適用します。

## 正本

- このディレクトリを現在の本番 GAS コードの正本として扱うこと。
- `../google-apps-script-playlist-submit.gs` は旧版であり、原則として編集しないこと。
- オンラインの Apps Script エディタとGitHubに差異が疑われる場合は、変更前に最新版を確認し、どちらを採用するかユーザーへ報告すること。

## 本番環境の保護

- **ユーザーの明示的な承認なしに、本番 Spotify プレイリストまたは本番 Google スプレッドシートへ書き込む操作を実行してはならない。**
- ユーザーの明示的な承認なしに、Spotify上の項目追加・削除・並べ替え、シートのセル・行・列・書式の変更、デプロイ、Script Propertiesの変更、トリガーの追加・削除・変更を行わないこと。
- `Test.js`、`test*`、`sync*`などの名前を安全性の根拠にしないこと。実行前に関数本体とすべての呼び出し先を確認し、外部サービスまたはシートへの書き込みの有無を判定すること。
- 調査・検証では静的解析、ローカルでの構文確認、モックまたは読み取り専用処理を優先すること。
- 本番操作の承認を得た場合も、対象、実行関数、予想される変更、ロールバック方法を実行前に明示し、必要最小限の操作だけを行うこと。

## 秘密情報

- Client Secret、アクセストークン、リフレッシュトークン、OAuth認可コード、共同編集者招待URL、署名鍵、認証ファイルをGitへコミットしないこと。
- 秘密情報は Apps Script の Script Properties 等、承認された秘密情報ストアで管理すること。
- 秘密値をログ、エラーメッセージ、テストフィクスチャ、README、Issue、コミットメッセージ、Pull Request本文へ出力しないこと。
- デバッグ時もPOST本文やAuthorizationヘッダーを丸ごと記録しないこと。

## 変更時の確認

- `doGet`、`doPost`、JSONP、レスポンス項目を変更するときは、`app/community.tsx`とのAPI契約を確認すること。
- `playlist`、`podcast`、`listenerPodcast`、`resolve`、`autoUpdateRequest`の既存契約を、Web側の対応変更なしに破壊しないこと。
- スプレッドシートの列番号や見出しを変更するときは、読込・書込の両方と既存データへの影響を確認すること。
- Spotify OAuthスコープ、リダイレクトURI、Webアプリの公開範囲を無断で変更しないこと。
- `appsscript.json`の変更は権限・公開範囲へ影響するものとして扱い、変更理由を明記すること。
- 自動更新処理では重複追加、ページネーション、同時実行、部分失敗、レート制限、再実行時の冪等性を確認すること。
- GASでは複数ファイルが同じグローバル名前空間を共有するため、関数名・定数名の衝突を確認すること。

## 同期とデプロイ

- ユーザーの明示的な依頼なしに、`git commit`、`git push`、Pull Request作成・更新、mergeを行わないこと。
- 調査・差分提示のみを依頼された場合は、Git履歴やリモート状態を変更しないこと。
- GitHubへのコミットと本番GASへのデプロイを別工程として扱うこと。
- `clasp push`、`clasp deploy`、オンラインGASへの貼り付け、本番トリガー操作は、ユーザーが明示的に依頼した場合のみ実行すること。
- `clasp push` の前には、必ず反映対象の差分をユーザーへ提示し、明示的な承認を得ること。
- `clasp push --force` は、通常の `clasp push` とは別に、その必要性と上書き対象を説明して明示的な承認を得ない限り使用しないこと。
- Apps Scriptエディタで変更されたコードを取り込む場合は、既存の未コミット変更を確認してから`clasp pull`し、意図しない上書きを防ぐこと。
- 時間トリガーはGitHubだけでは再現できないため、コード上の想定とApps Script側の実設定を区別して報告すること。

## 作業範囲

- ユーザーが指定したファイル以外を変更しないこと。
- 旧版ファイルを最新版へ機械的に同期しないこと。
- 大規模なファイル分割と機能変更を同じ変更に混在させないこと。
- コード整理時は、最初に挙動を維持した移動だけを行い、仕様変更は別のレビュー可能な変更に分けること。
